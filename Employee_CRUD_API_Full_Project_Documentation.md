# Employee CRUD API --- Full Project Documentation

## 1. Project Overview

**Project Name:** Employee CRUD API\
**Backend:** ASP.NET Core Web API\
**Framework:** .NET 6\
**Database:** PostgreSQL\
**ORM:** Entity Framework Core\
**API Documentation:** Swagger / OpenAPI\
**Authentication:** JWT (JSON Web Token)\
**Architecture:** Controller → Service → Repository → Database

The project started as an Employee CRUD API and has been progressively
enhanced with SOLID principles, department management, reporting,
PDF/Excel generation, email-based report delivery, logging, and JWT
authentication.

The planned final system is a full-stack Employee Management System with
a web UI connected to this backend.

# 6. Department Management

Employees are associated with departments through `DepartmentId`.

The database query used by the reporting functionality joins Employees
and Departments.

Example SQL generated by Entity Framework:

``` sql
SELECT
    e."EmployeeId",
    e."EmployeeName",
    e."Salary",
    e.created AS "Created",
    e."DepartmentId",
    d."DepartmentName"
FROM "Employees" AS e
LEFT JOIN "Departments" AS d
    ON e."DepartmentId" = d."DepartmentId";
```

This means an employee can be returned even when the department
relationship does not have a matching department record because the
query uses a LEFT JOIN.

# 9. DTOs

DTOs are used to separate API contracts from database entities.

Examples include:

``` text
EmployeeResponseDto
EmployeeReportDto
```

and request DTOs for creating/updating employees.

Benefits:

-   Prevent exposing database entities directly
-   Control API response fields
-   Keep request and response models separate
-   Make future API changes easier
-   Improve separation of concerns

# 10. SOLID Principles

The project is being developed as a practical SOLID example.

## S --- Single Responsibility Principle

Classes should have one primary responsibility.

Example:

``` text
Controller → HTTP/API responsibility
Service    → Business responsibility
Repository → Data-access responsibility
```

Avoid putting database queries, business rules, report generation, and
HTTP handling into one class.

------------------------------------------------------------------------

## O --- Open/Closed Principle

The project should allow new functionality without unnecessarily
modifying existing functionality.

For example, report delivery can evolve from:

``` text
Email
```

to:

``` text
Email
PDF
Excel
WhatsApp (future)
```

without putting every implementation into one large class.

------------------------------------------------------------------------

## L --- Liskov Substitution Principle

Implementations of interfaces should be usable wherever the interface is
expected.

Example:

``` text
IEmployeeRepository
       ↑
EmployeeRepository
```

The concrete repository should correctly implement the contract.

------------------------------------------------------------------------

## I --- Interface Segregation Principle

Interfaces should remain focused.

Instead of one huge interface containing unrelated functionality,
separate responsibilities where appropriate.

For example:

``` text
IEmployeeRepository
IEmployeeService
IReportService
IEmailService
```

------------------------------------------------------------------------

## D --- Dependency Inversion Principle

High-level classes should depend on abstractions rather than concrete
implementations.

Example:

``` csharp
private readonly IEmployeeRepository _employeeRepository;
```

The implementation is injected through dependency injection.

------------------------------------------------------------------------


# 13. Authentication vs Authorization

Authentication answers:

> Who is the user?

Authorization answers:

> What is this authenticated user allowed to do?

The project can be extended with roles such as:

``` text
Admin
Manager
Employee
```

Example:

``` csharp
[Authorize]
```

protects an endpoint from unauthenticated users.

Role-based authorization can use:

``` csharp
[Authorize(Roles = "Admin")]
```

when roles are configured in the JWT claims and application.

# 29. CORS

When the frontend runs on a different origin, ASP.NET Core must allow
the frontend origin.

Example local frontend:

``` text
http://localhost:5173
```

Example policy:

``` csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("FrontendPolicy", policy =>
    {
        policy
            .WithOrigins("http://localhost:5173")
            .AllowAnyHeader()
            .AllowAnyMethod();
    });
});
```

Then:

``` csharp
app.UseCors("FrontendPolicy");
```

The exact production origin must replace the localhost origin when
deployed.

# 32. Error Handling

A production-ready API should have centralized exception handling.

Recommended flow:

``` text
Controller
    ↓
Service
    ↓
Repository
    ↓
Exception
    ↓
Global Exception Middleware
    ↓
Standard API Error Response
```

Avoid adding repetitive `try/catch` blocks to every method when the
exception can be handled centrally.

Use local `try/catch` when the code can actually recover from or add
meaningful context to the exception.
